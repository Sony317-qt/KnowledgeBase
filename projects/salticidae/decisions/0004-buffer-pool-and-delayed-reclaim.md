# 0004. 缓冲池 + 延迟回收 + 左右通道资源不共用

## 背景

- 单帧 11264×9200 MONO8 ≈ **98.8 MiB**；分配一次需 20–24 ms，而帧间隔仅 ~8 ms。
- 驱动会复用 `fd->pData`，所以入队前至少要有一次 `memcpy`，这一步无法消除。
- 同一张图可能同时被融合、预览、存图三方引用。

## 候选方案

| 方案 | 优点 | 代价 |
|---|---|---|
| A 每帧 `new` 一块 | 逻辑简单 | 20–24 ms/帧的分配 >> 8 ms 帧间隔，必然丢帧 |
| B 缓冲池，归还即入 free | 分配归零 | 三方仍在引用时提前复用 → 数据被覆盖 |
| C 缓冲池 + refcount 延迟回收 | 既零分配又安全 | 内存占用上升（每通道上限 3 块） |

## 决定

选 C：

- 每通道池上限 `kMaxPooledInputBuffers = 3`。
- 归还时 `refcount > 1` 只进 `pending`，等所有引用释放才升级到 `free` —— **延迟回收**。
- **左右通道所有资源各有一把锁，绝不共用**：`fusionMutexes_[1..2]`、`inputPools_[1..2].mutex`、`leftMutex_` / `rightMutex_`、`leftQueue_` / `rightQueue_`。
- 入队用 `std::move`（O(1) 交棒）。

## 后果

- 放弃：内存占用上限被钉死在"每通道 3 块"，约 3 × 114 MB。
- **共用锁的后果**：先到的一路会吃掉全部缓冲，另一路每帧重新分配 130 MB —— 这是选 C 的直接理由。
- 发送侧同理：`spare` 池避免每帧重新分配（24 ms → 12 ms）；背压 = 丢最旧帧（6 GiB/通道预算）。

## 可被追问

1. 为什么不能零拷贝？——驱动复用 `pData`，必须拷一次；其余靠池 + 提前丢弃 + move 消除。
2. `refcount > 1` 为什么不能直接复用？——图可能同时被融合、预览、存图引用。
3. 左右为什么各一把锁？——共用会让一路吃掉全部资源，另一路每帧重分配。
4. `std::move` 到底做了什么？——只是类型转换，真正移动由移动构造完成，对 `cv::Mat` 是偷指针。
