# 0001. 相机由板端直接控制，PLC 只提供节拍

## 背景

- 现场已有 PLC（EL 单轴 / MMC 双轴）负责电机运动与光源。
- 一个自然的想法是"让 PLC 统一指挥一切"，包括触发相机。
- 但相机 SDK 的参数、启停、属性缓存都需要在进程内操作，PLC 只认识 ASCII 文本命令。

## 候选方案

| 方案 | 优点 | 代价 |
|---|---|---|
| A PLC 直接控制相机 | 时序最统一 | PLC 无法调 SDK；相机品牌差异全落到 PLC 脚本上 |
| B 板端控制相机，PLC 只给"到位"信号 | 相机能力完整可用；换相机只改插件 | 板端必须响应 `3`，否则丢拍 |
| C 板端定时轮询位置 | 不依赖 PLC 协议 | 8 ms 间隔下往返通信跟不上 |

## 决定

选 B，并在**两个层面分别表述**：

| 说法 | 含义 |
|---|---|
| 相机不受 PLC 控制 | **控制权**在板端：SDK 调用、参数、启停都由板端发起 |
| 拍照由 `3` 驱动 | **时机**由 PLC 决定：PLC 走到位才推 `3`，板端据此 `LSnapCamera` |

一句话：**PLC 提供节拍，板端执行动作。**

## 后果

- 放弃：PLC 侧的统一定时器与硬实时精度（板端是 Windows，不是 RTOS）。
- 得到：相机库完整能力 + 换相机只需换插件。
- 由此产生一连串连带设计：连续模式下 **14 次循环在 PLC 内部执行**，板端只被动响应 14 次 `3`；
  步进 / 停拍模式下循环才回到板端 `for`（见 [[projects/salticidae/README]] 8.4 一节）。

## 可被追问

1. "相机到底受谁控制？"——**分层回答**：控制权 vs 时机，别给单句答案。
2. 为什么不在板端做运动循环？——Windows 定时精度 + 8 ms 帧间隔，往返通信根本跟不上。
3. PLC 推 `3` 但板端相机还没就绪怎么办？——`softTriggerRejectStreak_` 连续被拒 5 次后本任务内不再调 `LSnapCamera`（外触发自适应）。
