# 0001. 拆三条线程：采集 / 测量 / UI 渲染

## 背景

- 相机 SDK 是**回调式**的：帧到达时在 SDK 的线程里回调，回调里不能做重活（阻塞会导致丢帧甚至 SDK 报错）
- UI 必须随时响应（拖动、缩放、渲染卡尺和点集），卡住会让操作员以为软件死了
- 测量是 CPU 密集的，耗时不可预测（元素数量、算法复杂度相关）

三者节奏完全不同，放在一条线程里必然互相拖累。

## 候选方案

| 方案 | 优点 | 代价 |
|---|---|---|
| A 单线程 + 事件循环 | 无锁、简单 | 一次测量就卡住 UI；SDK 回调里做重活会丢帧 |
| B 两线程（采集 / 主线程做测量+UI） | 改动小 | 测量仍会卡 UI |
| C 三线程（采集 / 测量 / UI） | 各自节奏独立，UI 永远不卡 | 需要跨线程交接与同步 |

## 决定

选 C。**采集线程只做"搬运"**（SDK 回调 → 转 `cv::Mat` → 更新最新帧缓冲），
**测量线程只吃最新帧**，**UI 线程只负责渲染**。

## 后果

- 放弃了"帧的完整性"：测量可能跳过中间的帧 —— 这是**故意的**，工业测量要的是"当前"。
- 引入了跨线程交接问题：显示侧必须拷贝，否则 UI 读到一半被相机覆盖 → 画面撕裂。
- 代价是内存带宽：1080p/30fps 的多次拷贝 ≈ 数百 MB/s。

## 可被追问

1. 为什么不是两条线程？（测量和 UI 谁让谁？）
2. 三条线程的调度优先级你设过吗？采集线程优先级应该更高还是更低？
3. 如果 SDK 回调线程和你的采集线程是同一个，会发生什么？
