# 0002. 帧交接：显示侧拷贝，测量侧读实时帧

## 背景

一帧 1080p RGB24 ≈ 6.2 MB。交接方式直接决定：会不会撕裂、要不要付拷贝带宽、UI 卡住会不会拖累采集。

## 候选方案

| 方案 | 优点 | 代价 |
|---|---|---|
| A 全部共享（传裸指针） | 零拷贝，最快 | 读写竞争 → 撕裂 / 数据不一致 |
| B 全部拷贝 | 绝对安全、解耦 | 每帧多次 6 MB 拷贝，带宽吃紧 |
| C 显示侧拷贝 + 测量侧读实时帧 | 兼顾安全与实时 | 测量侧存在被覆盖风险 |

## 决定

选 C：

- **显示侧**：`cv::Mat → QImage` 时**深拷贝**，再通过信号槽交给渲染线程；渲染线程用**生产者-消费者 + 帧变化判断**，锁内完成"判断 → 替换"。
- **测量侧**：从相机接口直接取**实时帧**，保证算的是当前状态。

## 后果

- UI 卡顿不会拖住采集（各走各的线程），也不会出现帧堆积（只保留最新帧）。
- **测量侧留下一个未验证的风险**：若算法入口没有深拷贝，且相机是**连续自由采集**，
  计算过程中缓冲被覆盖 → 算法读到半新半旧的撕裂图 → 测量结果不可信。
  目前依赖的假设是"算的时候相机不在写"，但这**没有被代码显式保证**。

## 待办（面试前必须弄清）

- [ ] 算法入口到底有没有 `clone()` / `copy()`？
- [ ] 相机是硬触发 / 软触发 / 连续采集？若是触发式，上面风险自然消失（前提写进文档）
- [ ] 若是连续采集，改成双缓冲 + 原子交换指针（或加一把轻量锁拷贝一次）
